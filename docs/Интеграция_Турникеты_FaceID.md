# Интеграция с турникетами Face ID (Hikvision) — план и архитектура

> **Статус:** проектная документация к согласованию. Реализация — после ревью.
> **Оборудование:** терминалы распознавания лиц Hikvision **DS-K1T670MX** (deltatech.kg).
> **Автор черновика:** Claude Code. **Дата:** 2026-07-20.

---

## 1. Цель и границы

**Что делаем.** Дети проходят через турникет, терминал распознаёт лицо (Face ID), фиксирует **вход/выход**, и это событие попадает в нашу ERP как «ребёнок физически был в комплексе в HH:MM».

**Что НЕ делаем (важно).** Турникет **не ставит отметку посещаемости** за тренера. Распознавание — это **журнал фактического присутствия** (check-in log). Отметку `present/absent/...` в занятии по-прежнему ставит **тренер вручную**. Данные турникета — это *подсказка/сверка* для тренера и *автозаполнение времени входа/выхода* для персональных тренировок.

| | Групповые занятия | Персональные тренировки (ПТ) |
|---|---|---|
| Кто ставит посещение | Тренер вручную (как сейчас) | Тренер вручную (как сейчас) |
| Что даёт турникет | Подсказка «вошёл в 17:42» рядом с ребёнком в экране тренера | Автозаполнение `entry_time` / `exit_time` (поля **уже есть** в `pt_lessons`) |
| Автоотметка | ❌ нет | ❌ нет (только время) |

> **Почему так.** Распознавание лица ≠ факт участия в тренировке. Ребёнок мог зайти в здание, но не прийти в зал; мог прийти на другую секцию. Ответственность за «был на тренировке» остаётся на тренере — это осознанное продуктовое решение.

## 2. Оборудование: Hikvision DS-K1T670MX

Ключевые характеристики (влияют на архитектуру):

| Параметр | Значение | Значение для нас |
|---|---|---|
| Протоколы | **ISAPI** (HTTP/REST), ISUP 5.0, TCP/IP | Интегрируемся по ISAPI |
| Аутентификация | **HTTP Digest** (RFC 2617, MD5) | Нужен digest-клиент; чувствителен к времени (NTP!) |
| Ёмкость лиц | **6 000** лиц на устройство | Хватает; при >6000 детей — шардинг по устройствам |
| Ёмкость событий | **150 000** событий (кольцевой буфер на устройстве) | Устройство переживёт долгий обрыв интернета |
| Скорость распознавания | < 0.2 c, точность > 99%, дистанция 0.3–3 м | Пропускная способность ~5 чел/сек на проход |
| Сеть | 10/100/1000 Мбит, IPv4/IPv6 | Ставится в локальную сеть комплекса |
| Двери | Управление до 2 дверей, 2 входа тревог | Вход/выход можно развести на 2 ридера |

**Три способа получать события с терминала (ISAPI):**

1. **HTTP Host Push** *(рекомендуется)* — терминал сам шлёт JSON-события на наш URL при каждом проходе. Реалтайм, минимум опросов.
2. **Alert Stream (listening)** — держим постоянное соединение `GET /ISAPI/Event/notification/alertStream`, парсим `multipart/mixed`. Fallback.
3. **AcsEvent search (pull)** — периодически опрашиваем `POST /ISAPI/AccessControl/AcsEvent` за период. Используем **только для сверки** (reconciliation) пропущенных событий.

Мы используем **(1) как основной канал + (3) как страховку**.

## 3. Ключевое решение: топология сети

Терминалы стоят **физически в комплексе (локальная сеть)**, а наша ERP — в облаке (Railway + Supabase). Это порождает главный архитектурный вопрос.

### Вариант A — прямой push терминал → облако (❌ не рекомендуется как основной)
Терминал шлёт события напрямую на публичный URL API.
- ➖ Терминал «смотрит в интернет» — Hikvision-устройства часто атакуют; риск безопасности.
- ➖ Push у Hikvision часто идёт по **HTTP без TLS** и слабой авторизацией.
- ➖ Регистрация лиц (заливка фото на терминал) требует, чтобы **облако достучалось до устройства в LAN** — а оно за NAT. Нужен проброс портов/VPN.
- ➖ При обрыве интернета события теряются, а дотянуться до устройства для сверки нельзя.

### Вариант B — локальный edge-агент на месте (✅ рекомендуется)
На комплексе ставим маленький **edge-агент** (мини-ПК / Raspberry Pi / NUC) в одной сети с турникетами. Он:
- принимает push-события от терминалов **локально** (быстро, надёжно, без выхода наружу);
- **регистрирует лица** на терминалах (ISAPI-запросы внутри LAN);
- **буферизирует** события в локальной SQLite при обрыве интернета;
- **пересылает** их в облако по HTTPS с секретным ключом, ретраями и идемпотентностью;
- периодически **сверяется** с терминалом (`AcsEvent`), чтобы не потерять ни одного прохода.

```
┌──────────────────────── КОМПЛЕКС (LAN) ────────────────────────┐
│                                                                 │
│   [Турникет вход ]──┐                                           │
│   DS-K1T670MX       │  push событий (ISAPI JSON, HTTP)          │
│                     ├──────────►  ┌─────────────────────────┐   │
│   [Турникет выход]──┘             │      EDGE-АГЕНТ          │   │
│   DS-K1T670MX      ◄──────────────│  (Python / FastAPI)     │   │
│        ▲   регистрация лиц (ISAPI │                         │   │
│        │   Digest, заливка фото)  │  • listener /hik/event  │   │
│        │                          │  • enroller (лица)      │   │
│        └──────────────────────────│  • SQLite буфер+ретрай  │   │
│                                   │  • reconciler (сверка)  │   │
│                                   └───────────┬─────────────┘   │
└───────────────────────────────────────────────┼───────────────┘
                              HTTPS + Bearer secret │ (исходящий)
                                                    ▼
                   ┌────────────────────────────────────────────┐
                   │      ОБЛАКО                                 │
                   │  Fastify API (Railway)                      │
                   │   POST /v1/hik/events   ← ingest события    │
                   │   POST /v1/hik/enroll   ← постановка в оч.  │
                   │           │                                 │
                   │           ▼                                 │
                   │  Supabase Postgres                          │
                   │   • access_events (журнал проходов)         │
                   │   • access_devices (реестр терминалов)      │
                   │   • children.access_person_no (связка)      │
                   └────────────────────────────────────────────┘
                                     │
                                     ▼
                   Экран тренера / ПТ: «вошёл в 17:42»
```

> **MVP-упрощение** (если хотим быстрее и без edge-агента на старте): терминал шлёт push напрямую в облако, а для управления/заливки лиц ставим лёгкий VPN (напр. Tailscale) на мини-ПК рядом с турникетом. Работает, но менее надёжно при обрывах и слабее по безопасности. Рекомендую сразу делать **Вариант B**.

## 4. Нужен ли отдельный стек (Python)?

**Да — только для edge-агента.** Разделяем на два компонента:

| Компонент | Где живёт | Стек | Почему |
|---|---|---|---|
| **Edge-агент** | На месте (LAN комплекса) | **Python 3.13 + FastAPI** (или Node — оба ок) | Изолированная задача: парсинг Hikvision-мультипарта, digest-auth, локальный буфер. Не смешиваем с бизнес-API. Python — отличный фит и то, о чём ты и думал. |
| **Cloud ingest** | Существующий backend (Railway) | **Fastify + TS** (как сейчас) | Новый роут `/v1/hik/*` в текущем backend. Валидация zod, запись в Supabase — уже вся инфраструктура есть. |

> **Почему edge-агент отдельным сервисом, а не внутри Fastify:** он должен работать **в локальной сети комплекса** (терминалы за NAT), переживать обрывы интернета и парсить нестандартный Hikvision-формат push (`multipart/form-data` со снимком лица + XML/JSON). Это другая зона ответственности и другое место развёртывания. Cloud-backend остаётся тонким и не знает про Digest/ISAPI.
>
> Python vs Node для агента — **не принципиально**. Python (FastAPI + `requests`/`httpx` с `HTTPDigestAuth`) читается проще для ISAPI и ты к нему склоняешься — берём его. Если захотим переиспользовать TS-стек команды — можно на Node, логика та же.

## 5. Поток 1 — Регистрация лица (enrollment): ERP → терминал

Чтобы турникет узнавал ребёнка, на терминал нужно залить: **карточку пользователя** + **фото лица**.

**Триггер:** админ/менеджер загрузил корректное фронтальное фото ребёнка (или нажал «Зарегистрировать на проходной»). Cloud кладёт задачу в очередь → edge-агент забирает и заливает на все терминалы.

**Шаг 1. Создать пользователя на терминале**
```http
POST /ISAPI/AccessControl/UserInfo/Record?format=json
Authorization: Digest ...
Content-Type: application/json

{
  "UserInfo": {
    "employeeNo": "100427",          // = children.access_person_no (наш стабильный ID)
    "name": "Айсулуу Асанова",
    "userType": "normal",
    "Valid": { "enable": true,
               "beginTime": "2026-01-01T00:00:00",
               "endTime": "2030-12-31T23:59:59" },
    "doorRight": "1",
    "RightPlan": [{ "doorNo": 1, "planTemplateNo": "1" }]
  }
}
```
Ответ: `{ "statusCode": 1, "statusString": "OK" }` (или `subStatusCode: "deviceUserAlreadyExist"` — трактуем как upsert, не ошибка).

**Шаг 2. Залить фото лица** (`multipart/form-data`, строгий порядок частей)
```http
POST /ISAPI/Intelligent/FDLib/FaceDataRecord?format=json
Content-Type: multipart/form-data; boundary=----hik...

--boundary  (часть FaceDataRecord, application/json)
{ "faceLibType": "blackFD", "FDID": "1", "FPID": "100427" }
--boundary  (часть FaceImage, image/jpeg)
<байты JPEG, ≤200 КБ, ≥80×80, одно фронтальное лицо>
--boundary--
```

**Требования к фото:** JPEG ≤ 200 КБ, ≥ 80×80 px, одно фронтальное лицо. Наши текущие фото из `children.photo_path` могут не подойти (обрезка/качество) → заводим **отдельное «фото для проходной»** с валидацией.

**Дерегистрация:** ребёнок архивирован/ушёл → edge-агент удаляет пользователя с терминалов (`DELETE UserInfo` по `employeeNo`).

## 6. Поток 2 — Проход (главный): терминал → edge → облако → БД

### 6.1. Что именно присылает турникет

При успешном распознавании терминал делает **HTTP-push** на edge-агент. Формат — `multipart/form-data`: JSON-часть события + (опционально) снимок с камеры. Ключевая структура события (`AccessControllerEvent`):

```json
{
  "ipAddress": "192.168.1.64",
  "portNo": 8000,
  "macAddress": "xx:xx:xx:xx:xx:xx",
  "dateTime": "2026-07-20T17:42:11+06:00",
  "activePostCount": 1,
  "eventType": "AccessControllerEvent",
  "eventState": "active",
  "AccessControllerEvent": {
    "deviceName": "Turnstile-Entrance",
    "majorEventType": 5,          // 5 = событие доступа
    "subEventType": 75,           // 75 = распознавание лица УСПЕШНО
    "employeeNoString": "100427", // ← НАШ ребёнок (access_person_no)
    "name": "Айсулуу Асанова",
    "cardReaderNo": 1,            // какой ридер: вход vs выход
    "doorNo": 1,
    "currentVerifyMode": "face",
    "serialNo": 88123,            // порядковый № события на устройстве
    "attendanceStatus": "checkIn",// checkIn / checkOut (если настроено)
    "userType": "normal",
    "faceURL": "http://192.168.1.64/.../snap.jpg"
  }
}
```

**Коды событий, которые нас интересуют** (`majorEventType = 5`):

| subEventType | Смысл | Действие |
|---|---|---|
| **75** | Лицо распознано успешно | Записываем проход ✅ |
| 76 | Лицо не распознано | Логируем (для аналитики/охраны), посещения не трогаем |
| 38 | Карта распознана | (если используем карты) записываем проход |

**Вход vs выход** различаем по `cardReaderNo` / `doorNo` / `attendanceStatus`:
- Ридер №1 (или дверь «на вход») → `direction = "in"` → `entry_time`.
- Ридер №2 (или «на выход») → `direction = "out"` → `exit_time`.

> ⚠️ **Аппаратный вопрос к поставщику:** чтобы фиксировать *и вход, и выход*, обычно нужно **два ридера/терминала** (вход и выход) либо терминал + выходной ридер. Один терминал даст только одно направление. Уточнить у deltatech.kg (см. §12).

### 6.2. Edge-агент → облако

Edge-агент нормализует событие и шлёт в облако компактный JSON (снимок **не** пересылаем — храним только факт и время):

```http
POST https://api.uniqum.../v1/hik/events
Authorization: Bearer <EDGE_SHARED_SECRET>
Idempotency-Key: <device_serial>:<serialNo>       // терминал+порядковый № = уникально
Content-Type: application/json

{
  "device_serial": "DS-K1T670MX-0512",
  "person_no": "100427",
  "event_serial": 88123,
  "event_type": "face_ok",         // face_ok | face_fail | card_ok
  "direction": "in",               // in | out | unknown
  "occurred_at": "2026-07-20T17:42:11+06:00"
}
```

### 6.3. Облако: обработка `POST /v1/hik/events`

Логика (новый роут в Fastify):
1. Проверить `Bearer` секрет edge-агента.
2. **Идемпотентность** по `Idempotency-Key` (`device_serial:event_serial`) — дубли отбрасываем (терминал/агент могут переслать повторно).
3. Найти ребёнка: `children.access_person_no = person_no`. Не нашли → пишем «unmatched» в лог (не падаем).
4. Вставить строку в `access_events`.
5. **Побочные эффекты (без автоотметки посещаемости):**
   - Если у ребёнка есть **ПТ-занятие** сегодня в окне ±90 мин → заполнить `pt_lessons.entry_time` / `exit_time` (это то, для чего поля уже заведены), `completed_source` не трогаем.
   - Для **групповых занятий** — ничего не автопроставляем; событие просто доступно экрану тренера как подсказка.
6. Ответ `200 { ok: true }`. Ошибки логируем, но 4xx не возвращаем зря — иначе агент будет бесконечно ретраить.

## 7. Изменения в модели данных (Supabase)

Новая миграция `2026xxxx_access_control.sql`:

```sql
-- Реестр терминалов
create table access_devices (
  id uuid primary key default uuid_generate_v4(),
  organization_id uuid not null references organizations(id),
  serial text unique not null,           -- device_serial
  name text not null,                     -- «Вход», «Выход»
  ip text,
  direction text check (direction in ('in','out','both')),
  last_seen_at timestamptz,
  is_active boolean not null default true,
  created_at timestamptz not null default now()
);

-- Журнал проходов (единственная новая «горячая» таблица)
create table access_events (
  id uuid primary key default uuid_generate_v4(),
  organization_id uuid not null references organizations(id),
  child_id uuid references children(id),          -- null, если лицо не сопоставлено
  device_serial text not null,
  event_serial bigint not null,
  event_type text not null,                        -- face_ok | face_fail | card_ok
  direction text not null default 'unknown',       -- in | out | unknown
  occurred_at timestamptz not null,
  created_at timestamptz not null default now(),
  unique (device_serial, event_serial)             -- идемпотентность на уровне БД
);
create index access_events_child_time on access_events (child_id, occurred_at desc);
create index access_events_org_time on access_events (organization_id, occurred_at desc);

-- Связка ребёнок ↔ терминал + статус регистрации лица
alter table children add column access_person_no text unique;   -- employeeNo на терминалах
alter table children add column face_photo_path text;           -- фото для проходной
alter table children add column face_enrolled_at timestamptz;   -- когда залито на терминалы
```

- `access_person_no` — стабильный числовой ID (генерим из последовательности), это `employeeNo` на всех терминалах. Не переиспользуем `card_number` (может быть null/меняться).
- `access_events` — единственная таблица с потоком записи. Индексы под запросы «проходы ребёнка» и «проходы за день».
- RLS: читать — admin/manager/coach своей организации; писать — только service role (backend).

## 8. Интеграция с существующим UI

- **Экран тренера (групповые занятия):** рядом с каждым ребёнком в списке занятия — маркер «🟢 вошёл 17:42» / «⚪ прохода нет», подтягивается из `access_events` за дату занятия. Тренер видит подсказку, **сам** жмёт `present/absent`. Опционально — кнопка «отметить всех вошедших» (пресет, не автокоммит).
- **Персональные тренировки:** `entry_time`/`exit_time` в `pt_lessons` заполняются автоматически из турникета (поля и эндпоинт `/v1/pt/lessons/:id/entry-exit` **уже существуют**). Тренер по-прежнему подтверждает проведение.
- **Карточка ребёнка (админ):** новая вкладка «Проходная» — статус регистрации лица, кнопка «Зарегистрировать/Перезалить фото», история проходов.
- **Настройки (админ):** раздел «Турникеты» — список `access_devices`, `last_seen_at` (жив ли терминал/агент), направление.

## 9. Расчёт нагрузки

Параметры (подставь реальные — прикинуто «с запасом»):

| Параметр | Оценка |
|---|---|
| Активных детей | ~1 000–2 000 |
| Посещений/день | ~800 |
| Событий/день (вход+выход) | ~1 600 |
| Пиковый слот (перед началом занятий) | ~150 детей за 15 мин ≈ **10/мин ≈ 0.17/сек** |
| Всплеск на одном проходе | до ~1–2/сек (предел терминала ~5/сек) |

**Выводы:**
- **Облачный ingest:** ~1 600 вставок/день — для Postgres это **пренебрежимо мало** (нагрузка «ниже шума»). Даже 10 000/день — ничто.
- **Трафик:** снимки лиц **не пересылаем** → событие ~200–300 байт. 1 600 × 300 Б ≈ **0.5 МБ/день**. (Если бы слали снимки по 60 КБ — было бы ~100 МБ/день; не нужно.)
- **Edge-агент:** справится даже Raspberry Pi 4 — задача I/O-лёгкая. Пики сглаживаются локальной очередью (SQLite).
- **Терминал:** распознавание < 0.2 с → узкое место не мы, а физическая пропускная способность прохода.

**Что реально требует внимания (не throughput):**
1. **Сглаживание пиков** — очередь на edge, чтобы всплеск прихода не бил залпом в облако.
2. **Идемпотентность** — терминал/агент могут переслать событие дважды (`unique(device_serial, event_serial)` в БД + `Idempotency-Key`).
3. **Обрыв интернета** — буфер на edge + `AcsEvent`-сверка. Терминал держит 150k событий, ничего не теряется.

Вывод: **производительность не проблема.** Инженерный фокус — надёжность доставки и корректная связка «лицо → ребёнок», а не масштаб.

## 10. Надёжность

- **Буфер на edge (SQLite):** событие сперва пишется локально, потом шлётся в облако; при обрыве копится и досылается.
- **Ретраи с backoff** + `Idempotency-Key` — безопасно повторять.
- **Reconciler:** раз в N минут edge опрашивает `POST /ISAPI/AccessControl/AcsEvent` (pull) и досылает то, что не ушло push’ем. Гарантия «ни одного пропущенного прохода».
- **Heartbeat:** edge раз в минуту дёргает `/v1/hik/heartbeat` → обновляем `access_devices.last_seen_at`; в UI видно, что терминал/агент живы.
- **NTP на терминалах обязателен** — Digest-auth и корректные таймстемпы ломаются при расхождении часов > 5 мин.

## 11. Безопасность

- Терминалы **не выставляем в интернет** — только LAN + edge-агент (Вариант B).
- Edge → облако: **HTTPS + Bearer-секрет** (отдельный от пользовательских JWT), ротация.
- Фото лиц — **биометрия (перс. данные)**. Хранить в приватном бакете, доступ по RLS, согласие родителей на обработку. Снимки проходов в облако не тянем — только факт+время.
- Пароли терминалов — сильные, не дефолтные; учётка ISAPI — отдельная сервисная.
- `access_person_no` — внутренний ID, не раскрывает ПДн.

## Резюме одним абзацем

Ставим на месте **edge-агент (Python/FastAPI)** в сети комплекса: он принимает push-события ISAPI с терминалов Hikvision, буферизует и надёжно пересылает в облако на новый роут `POST /v1/hik/events` (Fastify), который пишет в новую таблицу `access_events` и связывает проход с ребёнком через `children.access_person_no`. Регистрацию лиц агент делает по ISAPI (`UserInfo/Record` + `FaceDataRecord`). **Посещаемость по-прежнему ставит тренер** — турникет даёт лишь журнал присутствия (подсказка в UI) и автозаполнение `entry_time`/`exit_time` для ПТ (поля уже есть). Нагрузка ничтожна (~1.6k событий/день, ~0.5 МБ), реальный фокус — надёжность доставки и связка «лицо→ребёнок», а не производительность.
