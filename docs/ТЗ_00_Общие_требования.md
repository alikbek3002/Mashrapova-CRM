## 1. Цели и контекст

Uniqum Sport — детский спортивный центр в Бишкеке: ~1 000 активных воспитанников, 18 тренеров, 50 секций. Учёт сейчас распылён между **МобиФитнес + AMO CRM + Google Sheets** — данные дублируются, тренеры присылают отчёты вручную, у родителей нет доступа к информации о занятиях.

Фаза 1 заменяет эту связку **тремя веб-продуктами**:
1. **Админ-панель** — десктоп/планшет в браузере (директор, менеджеры, кассир)
2. **PWA тренера** — мобильный браузер по ссылке (журнал посещений)
3. **PWA родителя** — мобильный браузер по ссылке из WhatsApp (расписание + посещения + абонемент)

Двуязычный интерфейс: **ru** и **ky**, переключатель в шапке.

## 2. Технологический стек

### 2.1 Frontend
- **React 18** + **TypeScript** (`strict: true`, `noUncheckedIndexedAccess: true`)
- **Vite** — сборка и dev-сервер
- **React Router v6** — клиентская маршрутизация
- **TanStack Query (React Query)** — серверное состояние, кеш, инвалидация
- **react-hook-form** + **zod** + `@hookform/resolvers` — формы и валидация
- **date-fns** — даты
- **vite-plugin-pwa** — манифест и SW для тренера/родителя
- **@tanstack/react-virtual** — виртуализация длинных списков
- **@sentry/react** — мониторинг ошибок
- CSS custom properties (без препроцессора) — текущий подход проекта

### 2.2 Backend
- **Node.js 20 LTS** + **Fastify** + **TypeScript**
- **@supabase/supabase-js** — service-role клиент (только server-side)
- **zod** — валидация запросов (схемы переиспользуем с фронтом)
- **pino** — логирование
- **@fastify/helmet**, **@fastify/cors**, **@fastify/rate-limit**
- **@sentry/node**

Бэкенд — тонкий слой. Большинство CRUD идёт напрямую из фронта в Supabase через RLS-политики. Бэкенд закрывает только финансы, заморозки, форс-мажор, продажу карт, отправку уведомлений.

### 2.3 База данных
- **Supabase (Postgres 15)** — managed
- **RLS** на всех таблицах с пользовательскими данными
- **Supabase Auth** — email + magic link для admin/manager/coach; phone OTP для parent
- **Supabase Storage** — приватный bucket для фото детей и тренеров

### 2.4 Хостинг
- **Vercel** — фронтенд (Admin + Coach + Parent — единый SPA с роутингом)
- **Railway** — Node.js бэкенд
- **Supabase Cloud** — БД + Auth + Storage
- Домены: `erp.uniqumsport.kg` (admin), `coach.uniqumsport.kg`, `parent.uniqumsport.kg`

### 2.5 DevOps
- **GitHub** + **GitHub Actions** — typecheck + lint + build на каждый push
- **Vercel Preview Deployments** — превью на каждый PR
- **Dependabot** — еженедельные апдейты зависимостей
- **Sentry** (free tier) — мониторинг прода

```
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  Admin SPA   │  │  Coach PWA   │  │  Parent PWA  │
│   (Vercel)   │  │   (Vercel)   │  │   (Vercel)   │
└──────┬───────┘  └──────┬───────┘  └──────┬───────┘
       │                 │                 │
       └─────────┬───────┴─────────┬───────┘
                 ▼                 ▼
        ┌────────────────┐  ┌──────────────┐
        │  Supabase      │  │  Node API    │
        │  (Postgres,    │  │  (Railway,   │
        │   Auth, Storage│  │   Fastify)   │
        │   RLS)         │  │              │
        └────────────────┘  └──────────────┘
```

Принципы:
- **Single source of truth** — Supabase. Никакого дублирования.
- **Тонкий бэк** — только то, что нельзя безопасно сделать через RLS.
- **RLS-first** — каждая таблица защищена политиками.
- **Мульти-тенант с дня 1** — `organization_id` на всех таблицах.

## 4. Модель данных

Все основные сущности имеют: `organization_id`, `created_at`, `updated_at`, `deleted_at` (soft delete). Денежные поля — `numeric(12,2)`. Статусы — нативные Postgres `enum`.

### 4.1 Таблицы

| Таблица | Назначение |
|---|---|
| `organizations` | Заложено для мульти-тенанта |
| `profiles` | Все пользователи (admin/manager/cashier/coach/parent), расширяет `auth.users` |
| `families` | Семьи (родители) — один аккаунт = вся семья |
| `children` | Дети, привязка к `family_id` |
| `coaches` | Расширение profiles для роли coach (bio, achievements) |
| `sections` | Направления (гимнастика/единоборства/спец) с ценами |
| `groups` | Группа = секция + тренер + лимит + длительность |
| `group_schedule` | Регулярное расписание (день недели + время) |
| `lessons` | Конкретные занятия-инстансы |
| `enrollments` | Запись детей в группы |
| `club_cards` | Абонементы (monthly/quarterly/personal/single/trial) |
| `attendance` | Журнал посещений |
| `freezes` | Заморозки (pending/approved/rejected) |
| `payments` | Платежи (cash/terminal) |
| `progress_notes` | Заметки тренера о прогрессе |
| `notifications` | Системные уведомления (заморозка от тренера и т.п.) |
| `leads` | Лиды (база под АМО Фаза 3) |
| `audit_log` | Все критические действия |

### 4.2 Виртуальные сущности (VIEW)

`v_child_card_balance` — остаток занятий по карте: `total_lessons − attended_present + approved_freezes`. Используется фронтом и бэком, единственный источник правды для остатка.

`v_director_kpi` — агрегаты для дашборда: активных детей, выручка месяца, активных абонементов, заканчивающихся 7-дневных, загрузка по секциям.

### 4.3 Индексы (минимум)
- `children(family_id)`, `children(card_number)`, `children(full_name) GIN trigram`
- `lessons(date, group_id)`, `lessons(coach_id, date)`
- `attendance(lesson_id, child_id) UNIQUE`
- `club_cards(child_id, status)`
- `payments(child_id, paid_at DESC)`

## 5. Безопасность данных — реализуется с дня 1

### 5.1 Аутентификация
- **Admin/manager/coach** — email + magic link через Supabase Auth.
- **Parent** — phone OTP (WhatsApp); пароли не используем — родители их не помнят.
- **2FA для роли admin** — флаг `mfa_required` в `profiles`, включение в Фазе 1.5.
- Сессии — JWT в httpOnly cookie (или Supabase SDK с локальным хранением + auto-refresh).

### 5.2 Авторизация (RLS)
- RLS включена на ВСЕХ пользовательских таблицах. Default — DENY, политики разрешают точечно.
- **Manager/admin** — видит всё в своей `organization_id`.
- **Coach** — видит только детей из enrollments своих групп; пишет только `attendance`, `progress_notes`, `freezes` (как pending).
- **Parent** — видит только детей из своей `family_id`; никаких write-операций.
- **RLS на запись закрыта полностью** для: `payments`, `club_cards`, `freezes` (approve), `lessons.cancel` — эти операции идут только через бэкенд с `SUPABASE_SERVICE_ROLE_KEY`.

### 5.3 Секреты
- `SUPABASE_SERVICE_ROLE_KEY` живёт ТОЛЬКО в Railway env. Никогда во фронте, никогда в репо.
- `.env` в `.gitignore` с первого коммита; коммитим только `.env.example`.
- Все ключи — в Vercel/Railway secrets.
- GitHub Dependabot включён для `frontend/` и `backend/`.

### 5.4 Транспорт и инфраструктура
- HTTPS only (Vercel/Railway по умолчанию).
- CORS whitelist на бэке: только продовые и preview-домены Vercel из `FRONTEND_ORIGINS`.
- `@fastify/helmet` — CSP, HSTS, X-Frame-Options, Referrer-Policy.
- `@fastify/rate-limit`: 10 req/sec на `/auth/*`, 100 req/sec на остальное; глобальный лимит на IP.

### 5.5 Данные
- **Soft delete везде** (`deleted_at`); hard delete запрещён из UI. Восстановление — отдельная функция в админке.
- **Фото** детей и тренеров — приватный Supabase Storage bucket; раздача через **signed URLs** с TTL 1 час.
- **Деньги** — `numeric(12,2)`, никогда `float`.
- **`audit_log`** со дня 1: actor_id, action, entity, entity_id, before/after JSONB, ip, user_agent.
- **Идемпотентность** мутаций: `idempotency_key` (UUID) на платежах и продаже карт; бэк хранит ключи 24 часа в `idempotency_keys`.

### 5.6 Валидация и инъекции
- `zod`-схемы — единые для фронта и бэка (копия в обоих или общий пакет `shared/schemas`).
- Запрет `dangerouslySetInnerHTML` через ESLint-правило (`react/no-danger`).
- Только параметризованные запросы через Supabase JS / Postgres. Никаких raw concat.

### 5.7 Мониторинг и резервы
- **Sentry** на фронте и бэке (free tier).
- **Бэкап Supabase** ежедневный — Pro tariff включает; на free делаем GitHub Action `pg_dump` раз в день в Backblaze B2.
- **Health check** `GET /health` на бэке, Railway healthcheck каждые 30 сек.
- **Graceful shutdown** на SIGTERM (10 сек на завершение активных запросов).

### 5.8 PII и приватность
- Фото детей — никогда не публичные URL.
- Удаление по запросу — отдельный эндпоинт `DELETE /v1/family/:id/forget` (анонимизация PII в БД, hard delete фото).
- Логи — без PII (имена, телефоны, фото). В audit_log — только id-ссылки, имена там есть только в before/after изменений сущностей.

## 7. План работ — 3 недели (по КП)

### Неделя 1 — Фундамент
- Инфраструктура: Vercel + Supabase Cloud + Railway + домен + CI/CD
- БД: миграции 0001–0006, RLS, soft delete, индексы, audit_log
- Auth в админке (magic link)
- CRUD: дети, семьи, тренеры, секции, группы, справочники
- Sentry на фронте и бэке
- **Результат:** рабочая база и карточки

### Неделя 2 — Бизнес-операции
- Расписание: создание занятий, week/month вид, проверка конфликтов
- Клубные карты: продажа, статусы, расчёт остатка через `v_child_card_balance`
- Заморозки и форс-мажор
- Скидки: 500 сом на 2-го, индивидуальные
- Платежи (cash/terminal) с идемпотентностью
- **Результат:** продажи, расписание, заморозки

### Неделя 3 — PWA и запуск
- PWA тренера — все экраны
- PWA родителя — все экраны
- Дашборд обзвона + KPI директора
- UAT с командой Uniqum Sport
- Запуск в production + документация + инструктаж
- **Результат:** все три продукта в проде

## 8. Критерии приёмки

Фаза 1 завершена при выполнении ВСЕХ условий:

1. ✅ Менеджер входит в админ-панель, создаёт карточки, продаёт абонементы, ведёт обзвон
2. ✅ Тренер с телефона отмечает посещения без Google Sheets
3. ✅ Родитель по ссылке видит расписание, посещения, абонемент своего ребёнка
4. ✅ Заморозка инициируется тренером и подтверждается менеджером
5. ✅ Форс-мажор → +1 занятие всем детям группы
6. ✅ Расписание корректно, конфликты тренеров проверяются
7. ✅ Система работает 3 дня подряд без критических ошибок после UAT
