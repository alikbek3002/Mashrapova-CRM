## 1. Контекст и цели

### 1.1 Клуб

ОО «Академия Машрапова», город Ош, Кыргызстан. Один филиал, архитектура мультифилиальная (§1.3, §12.2).

| Параметр | Значение |
|---|---|
| Активных клиентов | ~525 |
| Новых в месяц | ~200 |
| Тренеров | ~15 |
| Дисциплины | бокс, ММА, вольная борьба, дзюдо, кикбоксинг, таэквондо |
| Плюс | фитнес-зона с отдельными абонементами и дежурным тренером на окладе |
| Языки интерфейса | русский и кыргызский (решение владельца от 25.09.2026; §12.1 требует только русский) |

### 1.2 Что заменяет система

CRM нет вообще. Лиды из Instagram идут цепочкой «директ → Telegram → менеджер», учёт живёт в
Google Sheets, оплата — наличными и терминалом (§1.2).

### 1.3 Куда направлен продукт

ТЗ §1.4 называет пять проблем, и четыре из пяти — это **воронка и удержание**, а не операционный учёт:

| Проблема (§1.4) | Модуль |
|---|---|
| 48–51% записавшихся не приходят на пробную | Воронка лидов, напоминания (§8, §9) |
| План продлений выполняется на 55% | Контроль срока абонемента, win-back (§4.5) |
| Работу менеджеров сложно проверить | KPI менеджеров, журнал действий (§7.4, §12.3) |
| Нет единой базы клиентов | Карточка семьи и ученика (§3) |
| Лиды из таргета обрабатываются медленно | SLA 10 минут и эскалация (§8.3) |
| ФОТ — 61% выручки | Зарплата 40% от выручки занятия (§10.1) |

Отсюда приоритет разработки: **дожим лида → первая продажа → удержание действующего клиента**.
Журнал посещений, расписание и касса — обслуживающий контур для этих трёх шагов, а не самоцель.

### 1.4 Чего в системе нет и не планируется

Движок форкнут из Uniqum Sport ERP (детский центр в Бишкеке) и содержал функции, которых в ТЗ
Академии нет ни в одном разделе. Они **удалены**, а не отключены:

| Что | Статус |
|---|---|
| Пропускная система, турникеты, терминалы на входе | удалено миграцией `20260924000001_drop_access_control.sql` |
| Face ID, распознавание лиц, фото лица клиента, биометрия | удалено там же (`children.face_photo_path`, `face_enrolled_at`, `access_person_no`) |
| Окна доступа по расписанию, авто-выход, команды дверям | удалено там же (`access_*` таблицы, `fn_access_windows`) |
| Проведение персональной тренировки «по турникету» | источник `turnstile` убран из `pt_sessions.completed_source` |
| Импорт из МобиФитнес, скрипты очистки данных Uniqum | удалено, `backend/scripts/` |
| Паспортные данные родителей, адрес, поле AmoCRM в формах | убраны из карточек (§3.2 их не требует) |

Исторические миграции, которые эти объекты создавали (`20260820000002..04`, `20260905000001`),
остаются в репозитории — их нельзя удалять, иначе не воспроизводится история базы. Смотреть на них
как на действующее требование нельзя: актуально то, что осталось после `20260924000001`.

Отдельно: «Пропускная система / Face ID» отсутствует и в плане версий §15, и в списке интеграций
§13. Вносить её обратно без нового требования от Академии — нельзя.

### 1.5 Три продукта

1. **Административная панель** — браузер на ПК или планшете: директор, управляющий, старший
   менеджер, менеджер, ресепшен (§12.1).
2. **Приложение тренера** — телефон, PWA по ссылке: посещаемость, заморозки, заметки, своя зарплата
   (§2.1, §6).
3. **Приложение родителя** — телефон, PWA: расписание, посещения, абонемент. По §15 это **версия
   2.0**; в движке оно уже есть и оставлено работающим (решение владельца от 25.09.2026).

## 2. Технологический стек — как реализовано

### 2.1 Frontend (`frontend/`)
- **React 18** + **TypeScript** (`strict`), сборка **Vite 5**
- **@tanstack/react-query** — серверное состояние, кеш, инвалидация; `PersistQueryClientProvider`
  + `query-async-storage-persister` — кеш чтения переживает офлайн (§12.4)
- **@supabase/supabase-js** — чтение и часть записи напрямую из фронта под RLS
- **vite-plugin-pwa** + **workbox-window** — манифест, service worker, автообновление
- CSS custom properties, без препроцессора (`src/styles.css`)
- Маршрутизации нет: активный экран — состояние в `AdminDashboard.tsx` / `CoachScreen.tsx` /
  `ParentScreen.tsx`. Роутер не подключался осознанно — навигация плоская, а глубокие ссылки
  офису не нужны.

### 2.2 Backend (`backend/`)
- **Node.js 22** + **Fastify 4** + **TypeScript**
- **@supabase/supabase-js** под `service_role` — только server-side
- **zod** — валидация тел запросов (`src/schemas/`)
- **pino** — логи; **@sentry/node** — ошибки
- **@fastify/helmet**, **cors**, **rate-limit**, **sensible**, **multipart**
- **minio** — необязательное файловое хранилище (альтернатива Supabase Storage, по env)

Бэкенд тонкий. Большинство чтения идёт из фронта в Supabase под RLS. Через бэкенд проходит то, что
нельзя доверить клиенту: деньги (продажа, платежи, возвраты, депозит), зарплаты, заморозки,
массовые операции с расписанием, рассылки, управление сотрудниками, загрузка файлов.

### 2.3 База данных
- **Supabase (Postgres)** — 95 миграций в `supabase/migrations/`
- **RLS на всех пользовательских таблицах**, default DENY
- **Supabase Auth** — вход по **телефону или email с паролем**. Телефон преобразуется в
  псевдо-email (`shared/auth/normalizePhone.ts`), потому что Supabase Auth ожидает email.
  Magic link и SMS-OTP не используются: SMS-провайдера нет (§13, открытый вопрос 1).
- **Supabase Auth MFA (TOTP)** — 2FA для директора и управляющего (§12.3)
- **Supabase Storage** — приватный bucket для фото учеников и тренеров, раздача по signed URL

### 2.4 Хостинг
- **Vercel** — фронтенд (единый SPA: админка, тренер, родитель)
- **Railway** — бэкенд Fastify, healthcheck `/health`
- **Supabase Cloud** — база, Auth, Storage
- Домен пока не выбран Академией — работают адреса Vercel и Railway (см. [DEPLOY.md](../DEPLOY.md))

### 2.5 DevOps
- **GitHub Actions**: `ci.yml` — typecheck и сборка; `backup.yml` — ночной `pg_dump` в Backblaze B2
- **Стенд миграций** `supabase/test/` — поднимает настоящий Postgres из npm-пакета без Docker,
  прогоняет все миграции и смоук-тест расчётов ТЗ (`npm run smoke`, `npm run tariffs`)

## 3. Архитектура

```
┌──────────────────────────────────────────────┐
│  Единый SPA (Vercel)                         │
│  ├── Админка      — десктоп, 5 офисных ролей │
│  ├── Тренер       — PWA                      │
│  └── Родитель     — PWA (v2.0)               │
└───────────────┬───────────────┬──────────────┘
                │ anon key      │ JWT
                │ + RLS         │
                ▼               ▼
       ┌────────────────┐  ┌──────────────────┐
       │  Supabase      │◄─┤  Fastify (Railway)│
       │  Postgres+RLS  │  │  service_role     │
       │  Auth, Storage │  │  деньги, зарплаты,│
       └────────────────┘  │  рассылки, файлы  │
                           └──────────────────┘
```

Принципы:
- **Единственный источник правды — база.** Расчёты живут в SQL (view и функции), а не на клиенте:
  клиентский расчёт упирался в `limit 5000` и на больших периодах врал.
- **RLS-first.** Каждая таблица защищена политиками; ошибка во фронте не даёт утечки.
- **Удаления нет.** Триггер `forbid_delete` на учётных таблицах, только архивирование (§2.2, §12.3).
- **Мультитенант с дня 1.** `organization_id` на всех таблицах — задел под §12.2.
- **Правила ТЗ — в данных, а не в коде,** где они будут меняться: нормативы SLA, пороги оттока,
  матрица каналов уведомлений, тексты сообщений, цены секций. Менять строку в базе дешевле деплоя.

## 5. Безопасность (§12.3)

### 5.1 Аутентификация
- Телефон или email + пароль через Supabase Auth, для всех ролей.
- **2FA (TOTP)** обязательна для директора и управляющего. Колонка `profiles.mfa_required` —
  источник правды, держится в синхроне с ролью триггером.
- Сброс утерянного фактора — `POST /v1/staff/:id/reset-mfa`, только директором и **не себе**:
  иначе достаточно угнать сессию.
- SMS-код как второй фактор не используется — провайдера нет (§13).

### 5.2 Авторизация
Матрица прав §2.2 реализована трижды и сверяется автоматически:
- **RLS-хелперы в Postgres** — `is_director()`, `can_manage_coaches()`, `can_manage_schedule()`,
  `can_view_finance_reports()`, `can_cancel_30pct()`.
- **`requireRole` в бэкенде** — на каждом денежном и административном маршруте.
- **`rbac.ts` во фронте** — гейтинг UI. Там же `TZ_MATRIX` и `auditRbacAgainstTz()`: в dev-сборке
  расхождения с таблицей §2.2 печатаются в консоль, чтобы дрейф от ТЗ был виден сразу.

Два намеренных отклонения от таблицы §2.2 занесены в `TZ_EXCEPTIONS` с причиной (§2.2 противоречит
§5.3 и §7.1, решено в пользу описания процесса):
- менеджер **управляет расписанием** — §5.3 «менеджер вносит изменение и указывает причину»;
- ресепшен **продаёт абонементы** — §7.1 «продаёт менеджер или ресепшен». Возвраты ему закрыты.

Видимость по ролям:
- **Тренер** — только свои группы и их ученики; пишет `attendance`, `lesson_notes`,
  `progress_notes`, заявку на заморозку (`pending`). Финансов клиента не видит, свою зарплату — да.
- **Родитель** — только дети своей семьи, только чтение.
- **Запись закрыта для всех ролей** на `payments`, `refunds`, `club_cards`, подтверждение заморозок,
  зарплаты — эти операции идут через бэкенд под `service_role`.

### 5.3 Деньги и идемпотентность
- `Idempotency-Key` на продаже абонемента, платежах, операциях с депозитом. Ключ создаётся **в
  момент постановки операции**, а не отправки — иначе повтор после оборванного соединения продал бы
  абонемент второй раз.
- Возврат ограничен фактически уплаченным (`refund_capped_at_paid` в логе) — формула §7.3 при
  сумме скидок выше 30% уводила бы клуб в минус.
- RESTRICTIVE-политика `mfa_required` через `mfa_satisfied()` на денежных и настроечных таблицах.

### 5.4 Данные
- **Удаление запрещено** триггером. Архив с восстановлением — отдельная страница.
- **Фото** — приватный bucket, signed URL с коротким TTL.
- **`audit_log`**: кто, что, когда, before/after.
- Логи без ПДн.

### 5.5 Транспорт
- HTTPS only. CORS whitelist из `FRONTEND_ORIGINS`.
- `helmet` — CSP, HSTS, X-Frame-Options. `rate-limit` — отдельно жёстче на аутентификацию.
- Только параметризованные запросы. `dangerouslySetInnerHTML` не используется.

## 6. Двуязычность

Русский и кыргызский — во всех трёх продуктах, переключатель в шапке, выбор хранится в
`localStorage`. Строки — объект `I18N` в `frontend/src/data.tsx`; двуязычные сущности базы
(`sections.name_ru` / `name_ky`, планы абонементов) хранят оба варианта.

Новые экраны пишутся сразу на двух языках. Решение владельца от 25.09.2026: Ош двуязычный,
кыргызский уже написан, выбрасывать его дороже, чем поддерживать.

## 7. Офлайн-режим (§12.4)

| Операция | Офлайн |
|---|---|
| Просмотр расписания и списков | ✅ кеш чтения React Query |
| Отметка посещаемости | ✅ очередь, идемпотентна по построению |
| Продажа за наличные | ✅ очередь с `Idempotency-Key` |
| Оплата терминалом | ❌ физически невозможна офлайн |
| Списание с депозита | ❌ нужна серверная проверка баланса |

Очередь — `shared/offline/outbox.ts` в `localStorage`, индикатор `OfflineBar`. Отправка по событию
`online`, при возврате на вкладку и раз в 30 секунд. Операции, отклонённые сервером, не пропадают
молча: офлайн-продажа — это уже взятые с клиента деньги, такие строки складываются в отдельный
журнал и показываются офису.

## 8. Критерии приёмки v1.0

Состав v1.0 задан §15. Проверяется сквозными сценариями:

1. Лид из Instagram заведён, менеджер связался — время первого контакта проставилось само;
   просрочка больше 10 минут подсвечена, через 30 минут ушла эскалация старшему (§8.3).
2. Лид записан на пробную с датой, группой и тренером; после пробной висит задача «предложить
   абонемент», а при неявке — задача позвонить через 3 часа (§8.2).
3. Менеджер продал абонемент: второму ребёнку семьи применилась скидка 500 сом, ручная скидка
   потребовала причину, платёж прошёл с идемпотентностью и записался в `audit_log` (§3.3, §7.1–7.2).
4. За 7 и за 3 дня до конца абонемента появились задачи менеджеру, в день окончания — тоже;
   через 3 дня после истечения создалось win-back-событие (§4.5).
5. Клиент без посещений 10+ дней помечен риском оттока, флаг снялся сам после первого посещения (§4.5).
6. Тренер отметил посещаемость с телефона, поставил заморозку — менеджер получил заявку `pending`;
   на месячном абонементе квота 0 заморозку не пропустила (§4.3).
7. Отмена занятия с причиной и виной: всем родителям группы ушло уведомление, всем ученикам
   начислилось +1 занятие, занятие по вине тренера не попало в зарплату (§4.4, §5.3).
8. Возврат посчитан по формуле §7.3 и не превысил фактически уплаченного.
9. Зарплата тренера: 2 500 / 12 × 40% = 83,33 за пришедшего ребёнка; аванс 20-го — 50%
   заработанного с 1-го по 20-е; управляющий скорректировал с причиной и утвердил (§10).
10. Дашборд директора показывает выручку с динамикой к прошлому периоду той же длины, конверсию
    «запись → приход», продления, топ менеджеров и зону риска (§11.1).
11. Директор без подтверждённого TOTP-фактора не проходит к денежным таблицам (§12.3).
12. Попытка удалить любую учётную запись отклоняется триггером (§2.2).

## 9. Что НЕ входит в v1.0

По §15 и §13:

| Функция | Когда | Что мешает сейчас |
|---|---|---|
| Реальная отправка SMS клиенту | v1.0 | нет договора с провайдером — открытый вопрос 1 |
| WhatsApp Business API | v1.0 | не выбран способ подключения — открытый вопрос 2 |
| Настоящий Web Push (закрытое приложение) | — | нужны service worker, VAPID, подписки |
| AmoCRM | v2.0 | §8 — временная замена CRM до подключения |
| Онлайн-оплата MBank | v2.0 | §7.2 — сейчас перевод отмечается вручную |
| Бонусная система, геймификация рефералки | v2.0 | журнал `referrals` заложен |
| Мультифилиальность | при 2-м филиале | `organization_id` уже везде |
| Спортивный магазин | не решено | открытый вопрос 8 |

Транспортный слой уведомлений (§9) построен целиком — матрица каналов, шаблоны с подстановками,
очередь `outbound_messages` с попытками и ошибками, массовая рассылка по фильтрам §9.2. Не хватает
только подключения провайдера: `SMS_PROVIDER=smskg` плюс четыре переменные в `backend/.env.example`.

**Пропускной системы, турникетов и Face ID в планах нет вовсе** — см. §1.4 этого документа.

## 10. Проверка миграций

`supabase/test/` — стенд на настоящем Postgres из npm-пакета, без Docker и прав администратора.

```bash
cd supabase/test
npm run migrate   # все миграции подряд
npm run smoke     # расчёты ТЗ
npm run tariffs   # доля занятия и зарплата по каждому тарифу
```

Смоук проверяет: зарплату 2500/12×40% = 83,33 (§10.1), базу возврата (§7.3), квоту заморозок (§4.3),
уведомление с подстановкой в шаблон (§9), ответ дашборда директора (§11.1), цену секции с откатом
на каталог (§5.1).

Границы стенда: `setup.sql` создаёт заглушки окружения Supabase (схема `auth`, `storage`, роли).
Это проверяет корректность SQL, но не поведение самого Supabase — прогон на dev-проекте не заменяет.
