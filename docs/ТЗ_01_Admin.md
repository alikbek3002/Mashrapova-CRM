## 1. Главный контур работы

Админка построена вокруг трёх шагов, которые §1.4 называет болью клуба. Всё остальное их обслуживает.

```
     ДОЖИМ ЛИДА                ПЕРВАЯ ПРОДАЖА              УДЕРЖАНИЕ
  ┌─────────────────┐       ┌──────────────────┐      ┌────────────────────┐
  │ Воронка лидов   │       │ Продажа          │      │ Контроль срока     │
  │ SLA 10 мин      │  ──►  │ абонемента       │ ──►  │ 7 / 3 / 0 дней     │
  │ эскалация 30 мин│       │ скидки, оплата   │      │ win-back, отток    │
  │ напоминания     │       │ запись в группу  │      │ должники, возвраты │
  └─────────────────┘       └──────────────────┘      └────────────────────┘
          §8                      §7, §3, §4                  §4.5, §11
```

Ежедневный сценарий менеджера: открыть **Воронку** → вкладка «Требуют действия» → обзвонить
просроченных лидов и клиентов с истекающим абонементом → продать → вернуться к нулю необработанных.

## 3. Воронка лидов (§8) — ядро системы

> §8 прямо называет модуль «упрощённой заменой CRM для первой версии». После подключения AmoCRM
> (v2.0, §13) он заменяется интеграцией, поэтому данные лида хранятся в форме, пригодной к выгрузке.

### 3.1 Карточка лида (§8.1)
Имя, телефон, **Instagram**, источник (`таргет` / `рекомендация` / `прямое обращение`), время
создания, ответственный менеджер, комментарии.

### 3.2 Этапы (§8.2)
`новый` → `связались` → `записан на пробную` → `пришёл` → `купил`.
Два тупика: `не пришёл` и `отказ` — **с обязательной причиной**, иначе воронка перестаёт объяснять,
где теряются деньги.

При записи на пробную фиксируются дата, время, группа и тренер — из них считается «запись → приход».

### 3.3 Нормативы SLA (§8.3) — то, ради чего модуль существует

| Событие | Норматив | Как реализовано |
|---|---|---|
| Первый контакт | ≤ 10 мин | отметка проставляется **сама** при уходе лида с этапа «новый» (триггер), менеджер её не ставит вручную |
| Эскалация | через 30 мин | строка краснеет, событие уходит старшему менеджеру |
| Напоминание о пробной | за 24 ч и за 2 ч | событие + задача менеджеру |
| Звонок после неявки | через 3 ч | задача «позвонить» |
| Конверсия после пробной | сразу | задача «предложить абонемент» |

Пороги живут в `org_settings` (`lead_first_contact_min`, `lead_escalation_min`,
`lead_no_show_hours`), а не в коде: §8.3 будет уточняться Академией.

Обновление — `refresh_lead_sla()`, вызывается планировщиком через `POST /v1/lifecycle/refresh`.

### 3.4 Экран
- Вкладка **«Требуют действия»** — открывается по умолчанию. Только то, где норматив нарушен или
  висит задача.
- Просрочка показана **в минутах прямо в строке**; эскалация — красным.
- В строке: WhatsApp, «Позвонить» (`tel:`), «Связались» (останавливает счётчик), «Записать на
  пробную», «Отказ».
- Фильтры по этапам, вкладка «Все».
- Сверху — плитки KPI менеджеров §7.4.

⚠️ Задачи SLA показываются здесь, а не в инбоксе: инбокса уведомлений у офиса пока нет — таблицу
`notifications` читает приложение родителя. Строки туда всё равно пишутся, так что при появлении
инбокса (§9.1, колонка «Менеджеру в системе») история уже будет.
⚠️ Напоминания клиенту за 24 ч и 2 ч сейчас уходят **задачей менеджеру**, а не в WhatsApp/SMS —
провайдера нет (§13).

### 3.5 KPI менеджеров (§7.4)
Все шесть метрик, функция `manager_kpi(from, to)`, плитки плюс разбивка по каждому менеджеру:

| Метрика | Цель |
|---|---|
| Скорость первого контакта | < 10 мин |
| Лид → запись на пробную | — |
| Запись → приход на пробную | > 70% |
| Пробная → продажа | — |
| Конверсия продлений | > 80% |
| Продаж в день | — |

Тот же источник питает дашборд директора и отчёты — чтобы цифры не разъезжались между экранами.

## 4. Удержание действующих клиентов (§4.5)

Второй по важности контур. Считается `refresh_card_notices()`, показывается на дашборде, в карточке
ученика и в списках.

| Событие | Клиенту | Менеджеру |
|---|---|---|
| За 7 дней до окончания | событие (SMS — при подключении провайдера) | задача |
| За 3 дня | событие с предложением длинного пакета | задача с пометкой «предложить пакет» |
| В день окончания | событие | задача позвонить |
| 3 дня после истечения | win-back «специальное предложение — 48 часов» | — |
| Нет посещений 10+ дней | — | флаг **«риск оттока»** на клиенте |
| Использована последняя тренировка | — | уведомление ресепшену, абонемент закрывается |

Детали:
- Флаг риска снимается автоматически при первом посещении; заморозка риском **не считается**.
- Порог — `org_settings.churn_no_visit_days`, не константа в коде.
- Закрытие абонемента по последней тренировке — смена поведения движка: раньше карта жила до
  `end_date` независимо от остатка. Это буква §4.5.

## 5. Клиенты (§3)

### 5.1 Поиск (§3.1)
По ФИО ученика, ФИО родителя, телефону, номеру карты / ID. Debounce, trigram-индексы.

### 5.2 Карточка семьи (§3.2)
ФИО и телефон отца, ФИО и телефон матери, **ответственный менеджер по продажам**, комментарии
(видны менеджерам и тренерам), список учеников. Один аккаунт = вся семья.

Паспортных данных и адреса нет — §3.2 их не требует, поля убраны из форм.

### 5.3 Карточка ученика (§3.2)
ФИО, дата рождения, фото (приватный bucket, signed URL), **дата регистрации**, **источник**
(таргет / рекомендация / другое), дисциплины (их может быть несколько), номер карты.

Статус цветом: активен · заморожен · истёк · должник · в архиве. Плюс бейдж **«риск оттока»**.

Вкладки:
- **Абонементы** — по одному на каждую секцию, остаток по каждому, период, заморозки.
- **Посещения** — **по каждому абонементу отдельно** (§3.2), а не общим списком.
- **Продажи** — дата, абонемент, сумма, менеджер (§3.2).
- **Заморозки** — дата, причина, инициатор, статус.
- **Успехи** — заметки тренера.
- **Комментарии администратора** — видны всем сотрудникам; не удаляются.

### 5.4 Скидки (§3.3)

| Скидка | Размер | Как работает |
|---|--:|---|
| Второй ребёнок из семьи | −500 | применяется автоматически при продаже |
| «Приведи друга» | −300 | журнал `referrals`: `pending → earned → used` |
| Индивидуальная | вручную | **причина обязательна** — проверяется и в RPC, и в форме |

Два решения, которых в ТЗ нет и которые ждут подтверждения Академии (вопрос 11):
бонус за друга становится доступен, **когда приведённый купил абонемент** (иначе −300 можно получить,
просто назвав любое имя), и он **суммируется** со скидкой на второго ребёнка, а не конкурирует с ней.

Журнал, а не разовая скидка, — потому что §3.3 требует заложить карточку со штампами под v2.0.

## 6. Абонементы (§4)

### 6.1 Каталог (§4.1, §4.2)
Правит только директор (`manage_card_plans`). Совпадает с таблицами ТЗ построчно:

| Тариф | Цена | Занятий | Срок | Заморозок |
|---|--:|--:|---|:-:|
| Детский · 1 месяц (через день) | 2 500 | 12 | 30 дн | 0 |
| Взрослый · 1 месяц (через день) | 2 800 | 12 | 30 дн | 0 |
| Пакет 3 месяца (−15%) | 6 375 | 36 | 90 дн | 1 |
| Пакет 6 месяцев (−20%) | 12 000 | 72 | 180 дн | 2 |
| Пакет 12 месяцев (−40%) | 18 000 | 144 | 360 дн | 3 |
| Разовое занятие | по секции | 1 | — | 0 |
| Пробная тренировка | по секции | 1 | — | 0 |
| Фитнес · каждый день | 3 000 | 26 | 30 дн | 0 |
| Фитнес · через день | 2 500 | 12 | 30 дн | 0 |
| Фитнес · комбо для ученика | +1 500 | 26 | 30 дн | 0 |
| Фитнес · разовое посещение | 400 | 1 | — | 0 |
| Фитнес · годовой (−30%) | 25 000 | 312 | 360 дн | 0 |

**12 занятий** в месячном абонементе подтверждены владельцем — это знаменатель цены одного занятия,
а значит и зарплаты тренера (§10.1). Значение живёт в `card_plans.lessons_count` и в снимке
`club_cards.total_lessons`, нигде не зашито в код.

Годовой фитнес заведён, но **неактивен**: §4.2 помечает «запуск в версии 2.0».
Срок 12-месячного пакета — 360 дней (12 × 30), согласуется с 90 и 180 в той же таблице.

### 6.2 Цены по секциям (§5.1, §4.1 «по секции»)
`sections.trial_price`, `single_price`, `subscription_price` — **переопределения**, а не замена
каталога. Одна точка правды — `section_price(section, type)`: цена секции главнее, пусто — цена
тарифа. Форма продажи берёт цену секции и пересчитывает при смене дисциплины.

Поля намеренно **не предзаполнены**: пустое означает «берётся из каталога» — это рабочее состояние.
Пустая строка сохраняется как `NULL`, а не ноль: ноль означал бы «бесплатно».
Месячные абонементы остаются клубными — §4.1 задаёт им единые цены для всех дисциплин.

### 6.3 Продажа (§7.1)
Точка входа — карточка клиента или расписание. Выбираются клиент (существующий или новый), секция,
тип абонемента, способ оплаты. Продажа привязывается к ответственному менеджеру.
Продают менеджер и **ресепшен** (§7.1).

Транзакция на бэкенде `POST /v1/cards/sell`: `club_cards` + `payments` + `audit_log`,
идемпотентность по `Idempotency-Key`. Ученик может ходить в несколько секций — на каждую свой
абонемент (§5.2).

### 6.4 Способы оплаты (§7.2)
Наличные · банковская карта (терминал) · перевод (MBank, Optima — отмечается вручную).
Плюс депозит ученика — механизм движка: пополнение и списание с идемпотентностью.
Автоматическая интеграция с платёжными системами — v2.0.

### 6.5 Заморозка (§4.3)
- Ставит менеджер (сразу `approved`) или тренер из приложения (`pending` → очередь в админке).
- **Лимит заморозок по типу абонемента** проверяется триггером `fn_check_freeze_quota`: на месячном
  абонементе квота 0, и заморозка просто не пройдёт. Проверка в базе, потому что заморозку создают
  три разных пути — офис через API, тренер через RLS, будущее приложение родителя.
- Срок абонемента продлевается на число дней заморозки.
- ⚠️ Потраченной квота считается по `approved_at`, а не по статусу: отгулянную заморозку
  `refresh_lifecycle` помечает `rejected`, и по статусу её не отличить от отказа офиса.

### 6.6 Форс-мажор и отмена занятия (§4.4, §5.3)
1. Менеджер или управляющий оформляет отмену **с причиной и виной**
   (`cancellation_fault`: coach / club / force_majeure / client / other).
2. Уведомление уходит **всем родителям группы**.
3. Всем ученикам начисляется **+1 занятие**: `total_lessons += 1`.
4. Занятие по вине тренера исключается из зарплаты явным условием в `v_payroll_attendance`.

⚠️ Это переделанный механизм. В движке Uniqum компенсация начислялась вставкой approved-**заморозки**
каждому ребёнку: заморозка двигает `end_date` на день, и это выдавали за компенсацию. Два изъяна —
это +1 **день срока**, а не +1 **занятие** (остаток и формула возврата §7.3 считаются по
`total_lessons`), и компенсация за вину клуба тратила заморозки **клиента**. После введения лимита
заморозок отмена на месячном абонементе вообще перестала бы проходить.

## 7. Расписание и секции (§5)

### 7.1 Карточка секции (§5.1)
Название (ru + ky), дисциплина, тренеры, **аудитория** (дети / взрослые / смешанная), цены секции,
филиал. Категории: `Единоборства` и `Фитнес-зона`.

### 7.2 Группа
Секция, тренер, дни недели и время (`group_schedule`), длительность, **жёсткий лимит учеников**.
Превышение возможно только вручную с подтверждением (§5.2). Занятия генерируются пачкой вперёд.

### 7.3 Виды расписания
Недельный (сетка с цветом по секции; клик → состав занятия) и месячный.
Конфликт тренера по времени проверяется на бэкенде → 409 с текстом.

### 7.4 Массовые операции
`bulk-generate` (генерация занятий по расписанию группы), `bulk-reschedule` (перенос),
`bulk-cancel` (отмена) — всё с причиной и виной.

## 8. Тренеры и зарплаты (§6, §10)

### 8.1 Карточка тренера (§6.1)
ФИО, фото, описание, достижения, телефон, дисциплины и секции, статус активен/архив.
**Денежные поля закрыты триггером** `forbid_coach_pay_change` — правят только директор и управляющий
(§2.2), тогда как био и достижения может править и старший менеджер.

### 8.2 Модели оплаты (§6.1, §10.1)

| Режим | Кому | Расчёт |
|---|---|---|
| `percent` | групповые занятия единоборств | **40%** доли занятия × число фактически пришедших |
| `fixed` | дежурный тренер фитнес-зоны | оклад 30–40 тыс. сом/мес |
| `per_child` | ставка за посещение | режим движка, оставлен как запасной |

Доля занятия = (цена абонемента − скидка) / число занятий; число берётся из снимка карты, иначе из
каталога. Если число не указано вовсе — расчёт откатывается на ставку группы и помечается
`rate_source = 'fallback_per_child'`, чтобы это было видно, а не превращалось в ноль.

Персональные тренировки — 50% стоимости (`pt_services.coach_percent_default`).
Пробные и занятия, отменённые по вине тренера, не оплачиваются.

Что это даёт по §1.4: ФОТ по групповым становится **40% вместо 61%** — больше 40% выручки
абонемента тренер получить не может по построению.

⚠️ Обратная сторона, вынесенная вопросом к Академии (вопрос 1): за ребёнка с годовым пакетом тренер
получает 50,00 против 83,33 за ребёнка с месячным — пакет продан со скидкой 40%, доля занятия
меньше. При этом клуб по §4.5 сам толкает клиентов в длинные пакеты.

### 8.3 Выплаты (§10.2, §10.3)
- **20-е число** — аванс: 50% заработанного с 1-го по 20-е (`compute_coach_advance`,
  `org_settings.advance_share_pct` / `advance_day`). В таблице видно «Аванс» и «К доплате».
- **5–10-е следующего месяца** — окончательный расчёт.
- Управляющий корректирует **с обязательной причиной** и утверждает; тренер видит начисления в
  приложении в реальном времени.
- Возврат абонемента уже начисленное тренеру не пересчитывает (§10.1).

## 9. Продажи, долги и возвраты (§7)

### 9.1 Платежи
Сумма, дата, метод, кто принял, комментарий. Только через `POST /v1/payments` с идемпотентностью.
Сверка по кассе: исправление нал/безнал у принятого платежа — отдельное право `correct_payments`.

### 9.2 Должники
Отдельная страница с бейджем в меню: ученики с подтверждённым долгом по абонементу. Выгрузка CSV
есть только в «Отчётах» — на самой странице должников её нет.

### 9.3 Возврат (§7.3)
```
Сумма возврата = (Оставшиеся тренировки / Всего тренировок) × Сумма абонемента − 30%
```
База — **цена тарифа**, как написано в §7.3. Возврат **без удержания 30%** — от старшего менеджера;
причина и имя сотрудника сохраняются.

**Предохранитель:** возврат не превышает фактически уплаченного (по платежам и списаниям с депозита).
Без него на скидках клуб уходил бы в минус — например, при тарифе 2 500 со скидками 800 клиент
заплатил 1 700, а формула вернула бы 1 750. Срезание пишется в лог (`refund_capped_at_paid`).
Это не изменение формулы, а защита от отрицательной маржи.

## 10. Уведомления (§9)

Матрица §9.1 хранится **таблицей** `notification_matrix`, а не кодом: открытый вопрос 3 прямо
говорит, что галочки Push/SMS ещё будут согласовываться — менять строку в базе дешевле деплоя.
Тексты — `message_templates` с подстановками вида `{child_name}`, правит Академия без разработчика.

Два разных «Push» разведены:
- **уведомление в приложении родителя** — работает: приложение читает `notifications`;
- **настоящий Web Push** при закрытом приложении — не сделан, нужны service worker, VAPID, подписки.

Push не попадает в очередь `outbound_messages` — она только для того, что уходит наружу через
провайдера (SMS). Лиду push не ставится: приложения у него нет по определению.

**Массовая рассылка (§9.2)** — `POST /v1/notifications/broadcast` от старшего менеджера: фильтры по
секции, тренеру, статусу абонемента и дате окончания, `dry_run`, одно сообщение на телефон.

## 11. Дашборд и отчёты (§11)

### 11.1 Дашборд директора (§11.1)
Функция `director_dashboard()` плюс три view:
- выручка за день / неделю / месяц **с динамикой к прошлому периоду той же длины** — месяц
  сравнивается month-to-date, иначе неполный текущий месяц всегда показывал бы падение;
- активные клиенты всего и по дисциплинам (`v_active_clients_by_section`);
- новые клиенты за период;
- конверсия «запись → приход» (цель > 70%) и продления (цель > 80%) — из `manager_kpi`;
- топ менеджеров по продажам и продлениям;
- **клиенты в зоне риска** (`v_clients_at_risk`): не приходили 10+ дней или абонемент истекает через 7;
- заполненность групп по секциям (`v_section_load`);
- активные ученики по дисциплинам, живые начисления тренерам за сегодня, посещаемость и расписание
  ближайших дней.

### 11.2–11.4 Отчёты
Три вкладки, всё считается в SQL и выгружается в CSV:

| Вкладка | Содержимое |
|---|---|
| Продажи | итоги за период, разрезы по менеджеру, типу абонемента и дисциплине (`sales_by_section`), конверсия «пробная → продажа», продления с ответственными, средний чек |
| Зарплаты | детализация по занятиям и группам (`payroll_detail`), колонка «Аванс», причина корректировки управляющего, статус выплаты словами |
| Операционные | посещения и пропуски по группам (`attendance_by_group`), история и частота по клиентам (`attendance_by_child`, частота — визитов в неделю), заполненность секций |

Считаем в SQL, а не на клиенте: прежний клиентский расчёт упирался в `limit 5000` и на больших
периодах просто врал.

## 14. Критерии приёмки админ-панели

1. Менеджер входит по телефону и паролю; директор без TOTP не попадает к денежным разделам.
2. Новый лид: счётчик норматива идёт, отметка первого контакта ставится **сама** при смене этапа,
   через 30 минут строка краснеет эскалацией.
3. Лид записан на пробную; после неявки во вкладке «Требуют действия» появилась задача позвонить.
4. Семья с двумя детьми: на втором абонементе применилась скидка 500 сом; ручная скидка без причины
   не сохраняется.
5. Продажа пишет `club_cards` + `payments` + `audit_log` одной транзакцией; повтор запроса с тем же
   `Idempotency-Key` не создаёт второй абонемент.
6. Заморозка на месячном абонементе отклоняется квотой; на трёхмесячном проходит и двигает `end_date`.
7. Отмена занятия по форс-мажору: +1 занятие всем ученикам группы, уведомление всем родителям,
   занятие по вине тренера не попало в зарплату.
8. Возврат считается по §7.3 и не превышает фактически уплаченного; срезание видно в логе.
9. Дашборд показывает динамику к прошлому периоду той же длины и список зоны риска.
10. Попытка удалить ученика, платёж или абонемент отклоняется триггером `forbid_delete`.
11. Все суммы — `numeric(12,2)`, без float-артефактов.
