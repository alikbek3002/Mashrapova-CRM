# Стенд для проверки миграций

Прогоняет все миграции и смоук-тест бизнес-логики на настоящем Postgres —
**без Docker и без прав администратора**. Postgres ставится как обычный
npm-пакет и запускается пользовательским процессом.

Появился после того, как двенадцать миграций подряд были написаны, но ни
разу не выполнены: в среде разработки не было ни базы, ни Docker, ни
Supabase CLI. Первый же прогон нашёл молчаливую поломку — настройки и
матрицу уведомлений новая организация не получала вовсе.

## Запуск

```bash
cd supabase/test
npm install
npm run db:start    # Postgres на 127.0.0.1:55432
npm run migrate     # все миграции по порядку
npm run smoke       # проверка расчётов ТЗ
npm run tariffs     # сколько тренер получает за ребёнка по каждому тарифу
npm run demo        # демонстрационные данные для интерфейса
npm run db:stop
```

## Что проверяет смоук-тест

| ТЗ | Проверка |
|---|---|
| §10.1 | Зарплата тренера: 2 500 сом / 12 занятий × 40% = 83,33 за пришедшего |
| §7.3 | База возврата — цена тарифа, но возврат не больше уплаченного |
| §4.3 | Квота заморозок: месячный абонемент (quota 0) заморозить нельзя |
| §9 | Матрица каналов и шаблоны засеяны; уведомление родителю порождает push и SMS с подстановкой |
| §11.1 | Функция дашборда директора отвечает |

## Демонстрационные данные

`npm run demo` наполняет базу так, чтобы интерфейсу было что показывать:
62 семьи, 82 ученика, 15 тренеров (один на фиксированной ставке — §6.2),
17 групп с расписанием, 83 абонемента, 273 занятия, около тысячи отметок
посещаемости, 80 платежей и 40 лидов на всех этапах воронки. В конце
вызываются `refresh_lifecycle()`, `refresh_card_notices()` и
`refresh_lead_sla()`, поэтому статусы, флаги оттока и задачи менеджера
посчитаны по календарю.

Это **не тест**: цель не проверить расчёт, а получить правдоподобную
картинку. Скрипт добавляет данные, а не пересоздаёт их — повторный запуск
удваивает объём.

## Как посмотреть интерфейс на этих данных

Фронтенд говорит с базой не напрямую, а через сервисы Supabase. PostgREST
поднимается отдельным бинарником, а вот GoTrue без Docker не поднять —
поэтому данные берём из базы, а вход оставляем демонстрационным.

1. Роль для PostgREST. Реального JWT нет, значит `auth.uid()` всегда
   пуст и RLS отсекала бы всё:

   ```sql
   create role local_api nologin bypassrls;
   grant usage on schema public to local_api;
   grant select, insert, update on all tables in schema public to local_api;
   grant execute on all functions in schema public to local_api;
   ```

2. PostgREST 16.4 (бинарник с GitHub) с такой конфигурацией:

   ```
   db-uri = "postgres://postgres@127.0.0.1:55432/postgres"
   db-schemas = "public"
   db-anon-role = "local_api"
   server-host = "127.0.0.1"
   server-port = 3000
   jwt-secret = "<случайные 32+ байта>"
   ```

   **`jwt-secret` обязателен, и это не про безопасность стенда.**
   `supabase-js` посылает заголовок `Authorization: Bearer <ключ>` в
   каждом запросе, даже когда никто не вошёл. PostgREST без секрета
   разобрать его не может и отвечает `500 PGRST300 Server lacks JWT
   secret` — **на всё**. Снаружи это выглядит как «страницы открываются,
   данных нет»: экраны показывают пустое состояние, потому что запрос
   завершился ошибкой, а не потому что база пуста. Проверить в одну
   команду:

   ```bash
   curl -s -H "Authorization: Bearer $TOKEN" 'http://127.0.0.1:3000/children?limit=1'
   ```

   Если он падает с `libpq.5.dylib not found`, библиотека лежит в самом
   пакете Postgres:

   ```bash
   export DYLD_FALLBACK_LIBRARY_PATH=node_modules/@embedded-postgres/darwin-arm64/native/lib
   ```

3. Ключ для фронтенда — JWT роли `local_api`, подписанный тем же
   секретом. Годится любой минтер, ставить зависимости не нужно:

   ```bash
   node -e 'const c=require("crypto"),s=process.argv[1],
     b=o=>Buffer.from(JSON.stringify(o)).toString("base64url"),
     h=b({alg:"HS256",typ:"JWT"}),
     p=b({role:"local_api",exp:Math.floor(Date.now()/1000)+31536000});
     console.log(h+"."+p+"."+c.createHmac("sha256",s).update(h+"."+p).digest("base64url"))' "<секрет>"
   ```

4. `frontend/.env` (файл в `.gitignore`, в прод не попадёт):

   ```
   VITE_SUPABASE_URL=http://127.0.0.1:3000
   VITE_SUPABASE_ANON_KEY=<токен из шага 3>
   VITE_DEMO_AUTH=true
   ```

   Vite читает `.env` только при старте — после правки перезапустите
   `npm run dev`, перезагрузки страницы недостаточно.

`VITE_DEMO_AUTH=true` включает вход по роли без пароля и подтягивает
настоящий профиль сотрудника из базы. Без флага заданный
`VITE_SUPABASE_URL` выключал демо-вход, и войти было нечем: настоящей
авторизации нет, а демо уже отключено.

Чтение работает полностью: дашборд, отчёты, воронка, списки, карточки.
Операции через бэкенд — продажа, возврат, аванс, отмена занятия — нет:
он ходит через `supabase-js` и требует настоящий `SUPABASE_URL`.

## Границы

`setup.sql` создаёт **заглушки** окружения Supabase: схему `auth` с
`uid()`, `jwt()`, `role()`, таблицы `auth.users` и `auth.mfa_factors`,
схему `storage` и роли `anon` / `authenticated` / `service_role`.

Это проверяет **корректность SQL**: типы, порядок зависимостей,
конфликты имён, работу триггеров и функций. Это **не** проверяет
поведение самого Supabase — выдачу JWT, реальный Storage, GoTrue MFA.
Прогон на dev-проекте Supabase он не заменяет.

Стенд работает под macOS arm64 (пакет `@embedded-postgres/darwin-arm64`).
Для другой платформы поменяйте путь к бинарникам в `start-db.mjs`.
